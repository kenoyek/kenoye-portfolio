When AI produces a large share of a patch, the engineering work changes shape. There is less time spent entering some kinds of code and more responsibility concentrated in the instructions, review, and verification around it.

My honest take is that an AI-heavy workflow is useful when it strengthens that loop. The volume of generated code tells me much less than whether the resulting system is understandable, correct, and ready for the people who depend on it.

Some work benefits from a fast first pass

Repetitive interface structure, straightforward transformations, and examples of an unfamiliar API can be good candidates for assistance. A draft can give you something concrete to question and improve.

Specific requests help. “Add a recoverable error state to this existing request” gives the assistant a narrower task than “make this page production-ready.” Existing types, surrounding code, and a description of the expected behaviour provide useful constraints.

I still treat the result as a proposal. Familiar-looking code deserves the same review as code written by a person, especially when it introduces a dependency or changes a shared abstraction.

The difficult decisions remain difficult

AI can produce an implementation of a permission check without establishing that the permission model is right. It can generate a database migration without knowing whether the source contains records that must be preserved. It can describe a deployment without proving that a live service works.

These are questions about the product and its operating environment. They require a clear account of who owns the data, which actions are authorised, what failure would mean, and what evidence is available.

For sensitive changes, I want a small, reviewable operation with a clear verification step. A successful command is useful evidence, but its meaning depends on what that command actually did.

Review the request path, not just the visible screen

A page can look complete while its data path remains fragile. Follow an interaction from the component to the helper, through configuration and authentication, and into the service response.

Check whether a public read unnecessarily depends on a signed-in session. Check whether a rejected request becomes an error state or a misleading empty list. Check whether a “saved” message appears only after the service confirms the write.

Those details often matter more to a user than the size or elegance of the generated patch.

Use tests to challenge the implementation

A test is most useful when it could reject a plausible but incorrect solution. For an article page, that might mean distinguishing a missing post from a failed request. For a migration, it could mean verifying that a conflicting import rolls back without replacing existing content.

Ask for failure cases as explicitly as the happy path: an expired session, an unavailable service, a slow response, a repeated submission, or a user without the necessary role.

Then inspect the test itself. A mocked success response can verify rendering, but it cannot prove that a remote database is reachable. Keep those conclusions separate so that a passing local suite does not become an unsupported claim about production.

Keep the changes small enough to explain

A large generated change can be expensive to review even when producing it was quick. Smaller steps make it easier to identify which assumption failed, preserve working behaviour, and reverse a decision.

Before accepting a patch, I want to explain what changed, why it is needed, how it was checked, and what remains uncertain. If that explanation is difficult, the change may need another pass.

This also helps with maintenance. The next engineer should be able to understand the system from its code, data model, tests, and documentation rather than needing the original conversation with an assistant.

The standard is still ownership

The useful question is whether AI assistance leaves you with a product you can support. That includes understanding its limits, acknowledging an unverified result, and making a recovery plan when something goes wrong.

I am interested in tools that make that work more effective. The responsibility for the shipped result stays with the engineer.
